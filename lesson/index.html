The lesson · 13 October 2026

Build a business that runs while you sleep.

In the workshop, one idea became a live page. Your next step is one useful routine that real people use, with checks and clear limits so it can run without you handling every result.

1 · Task vs loop

A task ends, but a loop runs again.

Asking AI to write one page is a task. A working loop waits for a trigger, makes a result, checks it, delivers or stops safely, and is ready for the next run. The trigger can be a new request or a schedule.

The diagram shows the routine, not proof that it earns money. A useful result still needs real users.

Task
One job with an end: write this page.
Workflow
Code fixes the route through the steps. A workflow can call AI and still follow a fixed route.
Agent
AI chooses its next steps or tools as it works toward a goal, within permissions you set.
Loop
A routine that can run again when triggered. It can contain a workflow, an agent, or both. Repeating alone does not make it an agent.

2 · One loop up close

Your idea became a live page in four steps.

The 60-Second Startup follows a fixed workflow. Code checks the output and a separate AI call reviews it. If it fails, the system tries one repair and checks again; if it still fails, it withholds the page.

3 · Three jobs to design

Grow. Serve. Improve.

Use these as three questions about your project. How will people find it? What useful result will they get? How will you learn what to change? People, workflows or agents can do these jobs; you do not need three autonomous systems on day one.

Grow
A useful page includes a link someone can share. That creates a route to the next user; the link alone does not prove that users will come.
Serve
Each new idea becomes a checked, live page.
Improve
After 15 ratings, the demo can propose new writing instructions, compare old and new on three fixed test prompts, and keep the change only if its checks pass and its test score improves.

This improvement changes instructions, not the model's training. A higher AI test score is evidence about those tests, not proof of happier customers. Check real user outcomes too.

4 · You stay in control

Let the routine run. Keep control of its limits.

“Without you” means no routine copy, click or send for each result. A server or other running system still needs to receive the trigger, keep state and do the work. You own its permissions, budget, exceptions and stop button.

Goals and limits
You

Choose the goal, limits and approvals.

Control panel

See results, costs, failures and work waiting for you. Pause new runs.

Allowed routine

Run only the actions you approved. Stop or ask for help outside that scope.

Runtime and saved state

A trigger, tools and a stored record of what happened, including what was already delivered.

Results and questions

Use code for rules you can state exactly. Use an AI review for judgment, with saved examples to test it. Neither catches every mistake. Decide in advance whether a failure means retry once, hold for review or stop.

5 · Build with AI

Describe, try, inspect, repeat.

Use an AI coding agent to build a small working version. Give it your goal, examples and limits. Ask for one testable step, inspect the result, and keep a version you can return to.

“Build the smallest version that turns this sample request into this useful result. First explain the steps. Then implement one step, show how to test it, and tell me what still needs a person.”

7 · From brief to a working loop

Build it in five testable steps.

Use your six lines as the specification. Build one small path all the way to a real result before adding more features.

1 · Input
Pick one real user and one request you can handle. Save a concrete example input and write the useful output they should receive. Start with a form, message or scheduled data source you have permission to use.
2 · First result
Ask your coding agent to make the smallest working path from that input to that output. Run it yourself once. Show the result to five people outside your team; find out whether it is useful.
3 · Check
Save good, bad and edge-case inputs. Define a pass/fail rule and test that it catches the bad results. Choose a safe failure action: a bounded retry, holding delivery for review, or stopping. Test the failure path too.
4 · Run again
Add the trigger or daily schedule, a running server, saved run status and delivery. Record what has already been sent so retries do not send duplicates. Test a restart and a failed delivery. Set limits, alerts and a stop control before leaving it unattended.
5 · Measure
Record real users, returning users, successful and failed deliveries, cost per useful result, and minutes of manual work. Review the evidence daily. Test one change at a time against saved cases and real user feedback.

A laptop script stops when its runtime stops. A hosted service still needs working credentials, scheduling, monitoring and someone responsible for exceptions. See the runbook before your unattended test.

8 · Keep going

One loop. Real users. Four weeks.

Use the challenge for the four-week milestones. Aim for at least 30 real users outside your team or 3 paying customers, at least two weeks running on its own every day, and people who come back week by week.
